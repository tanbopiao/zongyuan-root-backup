## 一、版本概述

V3.1 元闭环集成版将 V3.1 LLM 驱动算子生成器**深度集成**到 V3.0 六阶段元闭环引擎的算子规划阶段，实现"问题感知→算子匹配→LLM生成→守护校验→自评估→进化记忆"的完整自动化闭环。

### 核心突破

| 维度 | V3.0 元闭环 | V3.1 元闭环（LLM集成版） |
|------|------------|------------------------|
| 算子生成方式 | 3个硬编码模板填充 | 真实LLM代码生成（doubao-reasoning2） |
| 算子匹配池 | 仅V2注册表（~43算子） | 统一匹配池：V2 + V3.0 + V3.1 LLM生成（51算子） |
| 新算子入池 | 生成后注册到V3.0注册表 | 生成后立即加入运行时匹配池，后续问题可复用 |
| 自纠正机制 | 评估器迭代修复（最多N轮） | LLM内置3轮自纠正 + 评估器迭代（双重保障） |
| 算子来源追踪 | 无 | generation_method（llm/template_fallback/existing）+ llm_model + rounds |
| 回退策略 | 无 | LLM不可用→V3.0模板填充→完全失败标记 |

## 二、六阶段闭环架构

### 2.1 完整流水线

```
问题输入（自然语言描述）
        ↓
┌─ Stage 1: 问题感知 ──────────────────────┐
│  解析问题 → 提取关键词 → 时间戳            │
└────────────────┬──────────────────────────┘
                 ↓
┌─ Stage 2: 算子匹配（统一匹配池）──────────┐
│  匹配池: V2注册表 + V3.0生成 + V3.1 LLM生成 │
│  匹配策略: 关键词表(40+) + 词重叠率        │
│  命中 → 短路复用（跳过Stage 3-5）          │
│  未命中 → 进入Stage 3 LLM生成              │
└────────────────┬──────────────────────────┘
                 ↓ 未命中
┌─ Stage 3: 代码生成（LLM优先 + 模板回退）──┐
│  路径1: LLM auto_generate（生成+验证+评估+注册）│
│  路径2: V3.0模板填充回退                     │
│  路径3: 完全失败标记                          │
└────────────────┬──────────────────────────┘
                 ↓
┌─ Stage 4: 守护校验（MetaLoopGuardian）────┐
│  4公理校验: 非破坏性/可回滚/可验证/禁止危险操作│
│  AST危险扫描: 禁止os/subprocess/socket等     │
│  拒绝 → REJECTED，通过 → PROCEED            │
└────────────────┬──────────────────────────┘
                 ↓
┌─ Stage 5: 执行 + 自评估 ──────────────────┐
│  LLM算子: 使用生成器内置6维自评估分数        │
│  模板算子: 使用V3.0 CodeSelfEvaluator        │
│  通过阈值: ≥70分                             │
│  通过 → 加入匹配池（可复用）                 │
└────────────────┬──────────────────────────┘
                 ↓
┌─ Stage 6: 进化记忆 ───────────────────────┐
│  写入 evolution_memory_v31.jsonl            │
│  记录: problem/op_id/method/score/guardian  │
│  确权锚点 + DID + 内核版本                   │
└─────────────────────────────────────────────┘
```

### 2.2 统一算子匹配池

匹配池整合三个来源的算子：

| 来源 | 算子数 | 说明 |
|------|--------|------|
| V2注册表（operator_registry.json） | ~43 | 内核既有算子（14个实际代码算子+其他） |
| V3.0模板生成（generated_history） | 0-2 | V3.0演示中生成的算子 |
| V3.1 LLM生成（operator_registry_v31.json） | 8 | LLM真实生成的算子 |
| **运行时新增** | 动态 | 本次闭环中新生成并加入的算子 |
| **合计（演示结束时）** | **51** | |

匹配算法：
- 扩展关键词表（40+关键词，覆盖异常/校验/优化/均值/熵/相似度/标准化/排序/聚类/回归/过滤/统计等）
- 词重叠率（problem_words ∩ haystack_words / problem_words）
- 综合分 = 关键词分×2.0 + 重叠率×3.0
- 匹配阈值：综合分≥4.0

## 四、关键设计决策

### 4.1 为什么使用 auto_generate 而非 generate

- `generate()` 只做LLM生成+沙箱验证，不设置 self_eval_score
- `auto_generate()` 做完整流水线：生成→验证→自评估→注册，返回(artifact, score, grade)
- 元闭环Stage 3调用auto_generate，确保artifact携带自评估分数，Stage 5直接使用

### 4.2 为什么新算子立即加入匹配池

- 传统做法：算子生成后只写入注册表文件，下次启动才加载
- V3.1做法：生成验证通过后立即加入运行时匹配池，同一次批量进化中的后续问题可复用
- 收益：连续进化模式中，相似问题自动复用，减少LLM调用，降低成本

### 4.3 为什么匹配阈值设为4.0

- 关键词分（每个匹配+1，最多40+）× 2.0 = 最多80+
- 词重叠率（0-1）× 3.0 = 最多3.0
- 阈值4.0意味着：至少需要2个关键词匹配（4分）或1个关键词+高重叠率
- 过低会导致误匹配（不相关的算子被复用），过高会导致漏匹配（应该复用的算子重新生成）

## 五、安全防护

### 5.1 多层防护

| 层级 | 防护机制 | 位置 |
|------|---------|------|
| L1 | LLM系统提示词约束（禁止危险操作） | LLM生成器 |
| L2 | AST语法检查 | 沙箱验证器 |
| L3 | AST危险扫描（禁止os/subprocess/socket等） | 沙箱验证器 |
| L4 | 受限exec命名空间（仅安全内置+标准库） | 沙箱验证器 |
| L5 | 测试用例验证（TEST_INPUT+TEST_ASSERT） | 沙箱验证器 |
| L6 | MetaLoopGuardian 4公理校验 | 元闭环Stage 4 |
| L7 | 代码自评估（6维评分） | 元闭环Stage 5 |

### 5.2 元闭环守护4公理

- AXIOM-001: 非破坏性（算子不得修改外部状态）
- AXIOM-002: 可回滚（算子变更必须可回滚）
- AXIOM-003: 可验证（算子必须有测试用例）
- AXIOM-004: 禁止危险操作（os.system/exec/eval/subprocess等）

## 七、已知限制与V3.2优化方向

### 7.1 当前限制

1. **V3.0引擎不可用**：当前环境v3_meta_closed_loop.py的动态导入失败（operator_generator模块名不匹配），模板回退路径实际不可用。LLM生成是唯一可用路径。
2. **匹配算法为关键词匹配**：无语义嵌入，对于表述差异大的相似问题可能漏匹配。
3. **算子执行未集成**：匹配到算子后只返回op_id，未实际执行算子代码。
4. **无算子性能基准**：未测量算子执行时间和内存占用。
5. **进化记忆为JSONL追加**：无索引和查询能力。

### 7.2 V3.2优化方向

1. **修复V3.0模板回退**：修复operator_generator模块导入，确保LLM不可用时模板回退可用
2. **语义匹配**：引入sentence-transformers或LLM embedding，实现语义级算子匹配
3. **算子执行集成**：匹配到算子后自动加载并执行，返回执行结果
4. **算子性能基准**：自动测量每个算子的执行时间和内存占用，写入注册表
5. **进化记忆索引**：为evolution_memory_v31.jsonl建立索引，支持按问题/算子/分数查询
6. **批量进化优化**：连续进化模式中，先批量匹配再批量生成，减少重复LLM调用
